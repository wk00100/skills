# Git 慣例

其他 skill 的 PR／MR 說明格式與本檔不同時，依本檔。

## 本機客製

開始前先讀同資料夾的 `LOCAL.md`。檔案存在時，`LOCAL.md` 的規則優先於本檔，`LOCAL.md` 沒提到的部分照本檔。

理由：本檔跨裝置共用，工單系統、分支前綴、MR hook 依公司與 repo 而不同。`LOCAL.md` 列在 `.gitignore`，每台裝置各自維護，不進 repo。

## 分支命名

- `<type>/<英文 kebab-case 摘要>`，`<type>` 同 commit type。例：`fix/qa-pipeline`
- 一律不用中文

## Commit 訊息

- 標題用祈使句寫改動的結果：「切換帳號後重新載入目前帳號的資料」。不寫改動的理由（「切換帳號後畫面停在舊帳號資料」），也不寫實作方式（「改以 /api/me 確認結果」）
- 內文寫理由：改動前的問題、觸發條件與現象，不列改了哪些函式

理由：實作方式看 diff 就知道。標題讓讀者從 log 看出每個 commit 改變了什麼，內文回答 diff 回答不了的原因。

## MR 說明

**結構**：
- 標題沿用 commit 格式：`<type>: <摘要>`，`<type>` 取該分支 commit 的 type（`feat`、`fix`、`chore`、`docs` 等）。分支上有多種 type 時，取主要改動的 type
- 開頭兩句各佔一段：先寫為什麼改，再寫做了什麼
- 小標用 `###`，名稱依內容類型取（部署前提、注意事項、需驗證），不用「Review 重點」「要注意的設計」「未驗證」
- 改動清單接在開頭兩段後面，不設小標，每項改動寫成以 type 原文開頭的列點：`- fix: 開啟訂單明細時，明細內的請求使用列表選取行的 id`
- 小標與條列之間不空行
- 測試寫成該項的子項目：`  - 測試：<spec 檔名>`

**內容**：只寫 reviewer 需要的：改動原因、注意事項、部署前提、需驗證。
- 不逐檔重述 diff，不列已通過的測試數字
- 其他 repo 或上游的行為變化、發版順序不寫進本 repo 的 MR，記在交接文件

**條列**：
- 條件與後果寫完整：「A 與 B 一致，設定不一致時會得到 401」，不寫「其他一律 401」
- 一條只講一件事，前提或後果不同就拆開

開完 MR 後比對線上版本，使用者線上改過的地方回頭補進規則：所有裝置都適用的補進本檔，只有本機適用的補進 `LOCAL.md`。
