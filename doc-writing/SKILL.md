# 文件寫作規則

## 文件寫作（功能／行為說明）

以「讀者能理解、意義明確」為準：用白話 + 組合／矩陣 + 具體數字描述行為，例如「為所選使用者 × 部門 × 權限類型的每一種組合各建一筆，2 × 3 × 2 = 12 筆」。要避免**有模糊空間**的術語（「笛卡兒積」太模糊），不是禁用術語，意義明確不生歧義的術語照用。

重構前的現況盤點文件：事實（程式碼可證，附 `file:line`）與推測（意圖）分區塊寫，兩者不可混寫。只描述現況，不寫「應該怎麼改」。照猜錯的意圖重構會出錯。

**標題不寫會變動的數量**：標題與小標不寫「以下三點」「五個步驟」「兩種情況」等計數，內文開頭的引導句同樣不寫。條列增刪時標題不會跟著改，數字與內容對不上，而且不會報錯。要標示範圍就寫內容（「合併規則」「例外情況」），數量由條列本身呈現。回覆裡的標題比照辦理。

## 文件結構與 review

適用於所有文件：README、規格、操作說明、交接文件，以及給 agent 讀的 `AGENTS.md`、`CLAUDE.md`、skill。

**有先後順序的內容寫成步驟**：檢查或操作有先後順序時，寫成編號步驟，每一步附完成標準，不寫成段落或並列的參考條目。段落裡的判斷流程（先確認 A，沒有就做 B）同樣拆成步驟。並列的條目要讀者自己排順序，每次排法可能不同。只在步驟中途查閱的事實（API 路徑、各類差異）放在步驟後面的參考節，由步驟指過去。

**review 項目**：寫完或 review 時逐項檢查，結構依 `writing-for-agents` skill 的原則（給人讀的文件同樣適用），用字依 `~/.claude/CLAUDE.md` 的「回覆用字與語氣」。
- 同一條規則只寫在一處，原因與常見寫錯放在同一節。跨檔案也一樣，兩份文件內容重疊時，一邊改成指向另一邊
- 只在特定任務用到的內容（例：建立 tag 的流程）移到另一份文件，原文件留一行，寫明讀取時機與路徑
- 規則寫該做什麼。禁止句只留無法用正面寫法表達的限制，前面補上該做的事
- 讀者讀了沒有能做的事的條目（例：「CI 是否有差別未查」）刪掉，或移到記錄待查事項的地方
- 讀者不同的內容分開放：給維護者看的內容（驗證表、壓力測試表）不放進執行者讀的文件
- 每項事實對照程式碼核對，舊文件的說法不直接沿用

給 agent 讀的文件另外檢查：
- 常駐文件（`AGENTS.md`、`CLAUDE.md`）只放每個 session 都用得到的內容
- skill 由 description 觸發，其他文件不重複指向同一個 skill。保留的指向要寫出什麼情況下去讀
- description 先寫 skill 的用途，再寫觸發條件。內文不寫「使用時機」節重述 description

**結構要大改時開新檔重寫**：寫完給使用者看過再取代舊檔與 commit。在舊檔上改容易沿用舊的用詞與分節。

理由：2026-11-05 review crs、fbm 的說明檔與 skill 時，同一條規則在一份 skill 裡重複四到五處，有先後順序的檢查寫成並列段落，也有與程式碼不符的說法。`AGENTS.md`、`CLAUDE.md` 每個 session 都載入，多寫的內容每次都占 context。

## 交接文件只寫「現況 + 還沒做的」

寫或更新給下個 session 讀的文件（HANDOFF、README、NOTES）時，預設先刪再補。
使用者問「有能精簡的地方嗎」是精簡交接文件的信號。

**刪**：
- 變更紀錄：逐輪累積的「這輪改了什麼」，含標題裡的「（這輪改的）」、改名前後對照表
- 「已驗過」清單（只留**沒驗過什麼**，沒驗過的項目才影響下個人的第一步）
- 程式碼裡已有的東西（預設值表格、行數標註）改成指過去
- 決策理由壓成一到兩句，留在規則底下

**留**：
- 文件最後更新日期：單一時間戳，用來判斷文件是否過期
- 容易誤判的地方
- 同一參數在不同情境代表不同意思
- 改 A 時要一起改 B、漏了不會報錯的隱性連動
- 外部依賴為什麼破例（用了不該用的版本、繞過某個限制）
- 瀏覽器／平台支援限制

**結構**：「下輪要做的」與「知道但不打算做的」分兩節，不要混在一起重複列。

理由：交接文件是給下個 session 讀的，上一輪做過什麼對下個 session 沒有作用。複製自程式碼的內容，在程式碼修改後不會跟著更新。
