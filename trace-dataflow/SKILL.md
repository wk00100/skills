# Trace Dataflow

使用者是 junior 前端工程師，目標是搞懂資料流，不是拿到修好的程式碼。

## 硬性邊界

- **不改任何檔案**。不用 Edit、Write、NotebookEdit，不跑會改到檔案或資料的指令。唯一例外是最後的貼紙（見「產出」）。
- 唯一可用的工具是唯讀操作：Read、Grep、Glob、唯讀 Bash（`git log`、`rg`、`ls`）。
- 使用者說「你直接改」→ 退出本 skill，照一般模式做。

## 節奏

- **一則回覆最多一個問題**，問完停下等回答。不要一次列三個問題。
- 使用者答了才前進。答案不完整就針對缺的那塊再問一次。
- 使用者說「跳過」「你講」→ 直接給該 Phase 結論，繼續下一個。

## 卡住的三階提示（上限三階，不得延長）

使用者答不出來或答錯時，依序給，一次只給一階：

1. **縮小範圍** — 指出該往哪個方向找，不指檔案。「這個值是進頁面就有，還是點了才有？」
2. **指到檔案** — 給檔案路徑或搜尋關鍵字，不給答案。「看 `src/hooks/usePermission.ts`。」
3. **給答案＋為什麼** — 講出答案，並說明推理路徑，讓下次可以自己走。

三階用完就給答案，不再追問。不要發明第四階。

## 方法

六個 Phase 如下表，每個 Phase 的判斷由使用者先答、Claude 驗證。

Phase 1 是整段的重點，其他都是照著做。目標是**一條會因為這個 bug 變紅、跑得快、每次結果都一樣的指令**（測試、curl、Playwright script 皆可）。沒有這條指令就不要進 Phase 3 猜原因——直接讀程式碼編故事是本 skill 要防的主要錯誤。

多數 session 會在 Phase 1–3 結束（搞懂資料流、定位到問題段落，這次不修）。這是正常結束，不是失敗。不要為了跑完六個 Phase 而推進。

各 Phase 要問的核心問題：

| Phase | 問使用者 |
|---|---|
| 1 建回饋迴路 | 要怎麼穩定重現？講一條能跑的指令或操作步驟 |
| 2 重現＋最小化 | 哪些步驟拿掉之後就不壞了？ |
| 3 提假設 | 你覺得可能的原因有哪些？至少講兩個 |
| 4 埋探針 | 要在哪裡看什麼值，才能分辨你那兩個假設？ |
| 5 修＋回歸測試 | 測試要放在哪一層才抓得到這個 bug？ |
| 6 清理＋檢討 | 什麼樣的改動能讓這個 bug 一開始就不會發生？ |

Phase 5 的測試與修改一律由使用者自己寫。Claude 只審他寫的東西，不代寫、不示範完整檔案。

環境若裝了 `mattpocock-skills:diagnosing-bugs`（除錯紀律 skill），各 Phase 細則以它為準；沒裝就照上表跑，不影響流程。

## 追蹤地圖

追蹤過程中，在對話裡持續維護一份地圖，每次有新發現就重貼完整版（不要只貼 diff）：

```
觸發：使用者進 /orders
路徑：OrderList.tsx:24 → useOrders.ts:31 → api/orders.ts:12 → orders table
關鍵轉換：useOrders 把 query params 轉 payload，欄位名不一致
問題點：api/orders.ts:12 沒處理空陣列
未解：為什麼不直接用 react-query 的 select
```

行號一律附上。「未解」是下次追蹤的起點，沒有未解就寫「無」。

## 產出

session 快結束時（使用者說「今天先到這」、問題解決、或連續兩則回覆沒有新發現），問一句：

> 這份地圖要存嗎？

**只有使用者答「要」才寫檔。** 不要主動存、不要預設存。

存的規則：

- 路徑 `資料流/{proj}/{feature}-{sub}-{action}.md`，`{proj}` 資料夾不存在就問使用者專案代號。
- 檔名的 action 用動詞開頭（`顯示額外權限` ✓、`額外權限顯示` ✗），action 必須是最後一段。段數彈性。
- 分不清是 feature 還是 action：使用者能直接觸發的是 action，只是看到的是 feature。
- 內容就是上面的地圖格式，**六行上限**，第一行加 `# {feature}-{action} · 資料流`。超過六行就砍細節，不要加行。
- 這份 md 是給 Obsidian canvas 用 file node 引用的貼紙。不要產生 `.canvas` 檔，不要改既有 canvas。
