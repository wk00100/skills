# Trace Dataflow

使用者是 junior 前端工程師，目標是理解資料流，不是拿到修好的程式碼。

## 硬性邊界

- **不改任何檔案**。不用 Edit、Write、NotebookEdit，不執行會改到檔案或資料的指令。唯一例外是最後的貼紙檔（見「產出」）。
- 只用唯讀操作：Read、Grep、Glob、唯讀 Bash（`git log`、`rg`、`ls`）。
- 使用者說「你直接改」→ 退出本 skill，照一般模式做。

## 節奏

- **一則回覆最多一個問題**，問完停下等回答。不一次列多個問題。
- 使用者回答後才前進。答案不完整就針對缺少的部分再問一次。
- 使用者說「跳過」「你講」→ 直接給該 Phase 結論，繼續下一個。

## 答不出來時的提示（上限三階，不得延長）

使用者答不出來或答錯時，依序給，一次只給一階：

1. **縮小範圍**：指出該往哪個方向找，不指檔案。「這個值是進頁面就有，還是點了才有？」
2. **指到檔案**：給檔案路徑或搜尋關鍵字，不給答案。「看 `src/hooks/usePermission.ts`。」
3. **給答案與理由**：講出答案並說明推理路徑，讓使用者下次能自己推出來。

三階用完就給答案，不再追問，不增加第四階。

## 方法

各 Phase 列在下表，每個 Phase 的判斷由使用者先答、Claude 驗證。

Phase 1 是整段流程的重點，其他 Phase 照表執行。Phase 1 的目標是**一條會因為目前的 bug 失敗、執行快、每次結果都一樣的指令**（測試、curl、Playwright script 皆可）。沒有該指令就不進 Phase 3 推測原因。本 skill 主要防止的錯誤：沒有重現手段就直接讀程式碼推測原因。

多數 session 會在 Phase 1 到 3 結束（理解資料流、定位到問題段落，本次不修）。屬於正常結束，不算失敗。不為了走完所有 Phase 而推進。

各 Phase 要問的核心問題：

| Phase | 問使用者 |
|---|---|
| 1 建回饋迴路 | 要怎麼穩定重現？講一條能跑的指令或操作步驟 |
| 2 重現＋最小化 | 哪些步驟拿掉之後就不會出錯？ |
| 3 提假設 | 你覺得可能的原因有哪些？至少講兩個 |
| 4 加觀察點 | 要在哪裡看什麼值，才能分辨你提的兩個假設？ |
| 5 修＋回歸測試 | 測試要放在哪一層才抓得到目前的 bug？ |
| 6 清理＋檢討 | 什麼樣的改動能讓同類 bug 一開始就不會發生？ |

Phase 5 的測試與修改一律由使用者自己寫。Claude 只審查使用者寫的內容，不代寫、不示範完整檔案。

環境若裝了 `mattpocock-skills:diagnosing-bugs`（除錯流程 skill），各 Phase 細則以該 skill 為準。沒裝就照上表執行，不影響流程。

## 追蹤地圖

追蹤過程中，在對話裡持續維護一份地圖，每次有新發現就重貼完整版（不只貼 diff）：

```
觸發：使用者進 /orders
路徑：OrderList.tsx:24 → useOrders.ts:31 → api/orders.ts:12 → orders table
關鍵轉換：useOrders 把 query params 轉 payload，欄位名不一致
問題點：api/orders.ts:12 沒處理空陣列
未解：為什麼不直接用 react-query 的 select
```

行號一律附上。「未解」是下次追蹤的起點，沒有未解就寫「無」。

## 產出

session 快結束時（使用者說「今天先到這」、問題解決、或連續兩則回覆沒有新發現），問一句：

> 這份地圖要存嗎？

**只有使用者答「要」才寫檔。** 不主動存，不預設存。

存檔規則：

- 路徑 `資料流/{proj}/{feature}-{sub}-{action}.md`，`{proj}` 資料夾不存在就問使用者專案代號。
- 檔名的 action 用動詞開頭（寫 `顯示額外權限`，不寫 `額外權限顯示`），action 必須是最後一段。段數不限。
- 分不清 feature 與 action 時：使用者能直接觸發的屬於 action，只能看到的屬於 feature。
- 內容照上方地圖格式，**六行上限**，第一行加 `# {feature}-{action} · 資料流`。超過六行就刪細節，不加行。
- 存下的 md 是貼紙檔，給 Obsidian canvas 以 file node 引用。不產生 `.canvas` 檔，不改既有 canvas。
